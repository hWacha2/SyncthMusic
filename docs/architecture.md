# Архитектура SynctMusic

Версия документа: 0.1 (design). Все решения ниже — рекомендации с обоснованием;
спорные места помечены **ADR-кандидатами**.

---

## 1. Принципы

1. **Local-first.** Каждое устройство полностью работоспособно офлайн и является
   полноправной репликой библиотеки. Сеть нужна только для обмена дельтами.
2. **Нет обязательного сервера.** Любой сетевой компонент (релей, rendezvous,
   store-and-forward) заменяем и опционален.
3. **Данные важнее файлов.** Плейлисты, лайки, история, теги — это состояние
   библиотеки, а не побочный продукт файловой системы.
4. **Никогда не терять данные пользователя.** Удаление — через tombstones + корзину;
   файлы пользователя не перезаписываются и не перемещаются без явного согласия.
5. **Файлы не покидают доверенный круг.** Передача только между устройствами с
   ключом той же библиотеки. Никакой публичной раздачи.

## 2. Почему без сервера — и что вместо него

| Функция сервера | Замена |
|---|---|
| Хранение манифеста | CRDT-лог, полная реплика на каждом устройстве |
| Доставка дельт, когда пир офлайн | «Глупая труба»: папка/WebDAV/Nostr/git (store-and-forward) |
| Аутентификация | Подписи операций ключом устройства |
| Rendezvous (кто где) | Iroh: Pkarr/DNS-резолв по pubkey + hole punching |
| Relay для NAT | Iroh-релей для сигналинга (КБ); фолбэк байтов — выключен по умолчанию |
| Поиск/каталог | Локальный SQLite + FTS5 |

Ключевой момент: **манифест отделён от транспорта**. Лог операций — это
самодостаточный набор подписанных иммутабельных объектов. Их можно доставить
хоть по почте на флешке; результат слияния будет одинаковым.

## 3. Компоненты

```
crates/
  core/        # вся логика: scan, hash, db, crdt, transport, policy, player-ctl
  cli/         # syncth: диагностика, headless-демон, e2e-тесты
  ffi/         # flutter_rust_bridge glue
app/           # Flutter UI (desktop + Android + iOS)
docs/
```

`core` не знает про UI и не содержит платформенного кода, кроме тонких трейтов:

```rust
trait BlobStore { fn put(&self, r: impl Read) -> Result<BlobId>; fn get(&self, id: &BlobId) -> Result<Box<dyn Read + Send>>; }
trait Platform { fn data_dir(&self) -> PathBuf; fn is_metered(&self) -> bool; fn is_charging(&self) -> bool; fn notify(&self, e: Event); }
trait Pipe     { fn push_ops(&self, ops: &[Op]) -> Result<()>; fn pull_ops(&self, since: Hlc) -> Result<Vec<Op>>; }
```

## 4. Идентичность и пейринг

- **Устройство:** Ed25519 keypair. `device_id = base32(pubkey)`. Приватный ключ —
  файл `identity.key` с правами 0600 (на Android — в Keystore, на iOS — Keychain).
- **Библиотека:** `library_id = BLAKE3(root_pubkey)`. Первое устройство генерирует
  root-ключ; остальные получают его при пейринге. Root-ключ подписывает «членство»
  (`member.add` / `member.revoke`) — это и есть access control.
- **Пейринг:** QR/строка вида `syncth://pair?lib=..&dev=..&key=..&addr=..`
  (адрес — LAN IP + порт + отпечаток TLS). Дополнительно: 6-словный код
  (BIP39-подобный) для ручного ввода. Пейринг передаёт root-ключ библиотеки —
  поэтому только по доверенному каналу (face-to-face).
- **Отзыв устройства:** `member.revoke` + ротация root-ключа (новый epoch).
  Старые операции остаются валидными; новые — только для нового epoch.

## 5. Модель данных

### 5.1 Две идентичности

| Сущность | Что это | Как считается |
|---|---|---|
| `blob_id` | физический файл | `BLAKE3(bytes)` |
| `track_id` | логическая запись | `BLAKE3(chromaprint \|\| duration_ms)`; фолбэк — нормализованные `artist+title+duration` |

Один трек → много блобов (mp3/FLAC/opus, разные мастеринги). Блоб → максимум один
трек. Связь: `blob.track = track_id`.

Это решает пункт «разные теги при одном и том же аудио»: теги меняют `blob_id`, но
не `track_id`. Передача нужна только если у пира нет *эквивалентного* блоба
(проверка по `track_id` + качеству), а не по имени файла.

### 5.2 Операция (атом репликации)

```jsonc
{
  "id":     "b3:9f2c...",          // BLAKE3 канонического тела
  "lib":    "lib_7Qa...",           // library_id
  "dev":    "dev_3Kx...",           // автор (pubkey)
  "epoch":  1,                      // эпоха root-ключа
  "hlc":    [1767225600123, 4],     // [unix_ms, counter] — Hybrid Logical Clock
  "kind":   "track.upsert",
  "body":   { /* см. ниже */ },
  "sig":    "ed25519:..."
}
```

Свойства: иммутабельна, идемпотентна (по `id`), проверяема без сервера,
сериализуется в 200–800 байт.

### 5.3 Типы операций

| kind | семантика CRDT | назначение |
|---|---|---|
| `blob.have` | grow-only set `(dev, blob)` | «у меня есть файл» |
| `blob.drop` | per-device LWW по HLC | «я удалил копию у себя» (освобождение места) |
| `blob.derived` | LWW | «этот блоб — транскод того-то» (opus для телефона) |
| `track.upsert` | field-level LWW + ранг источника | метаданные (название, артист, альбом, год, MBID…) |
| `track.remove` | LWW-register (tombstone) | «убрать из библиотеки везде» |
| `track.pin` | OR-set по `(dev, track)` | политика хранения на устройстве |
| `track.rate` | LWW | оценка 0–5 |
| `like` | OR-set `(dev, track)` | лайк |
| `playlist.set` | LWW (имя, правила) | плейлист |
| `playlist.item` | fractional index + tombstones | порядок треков |
| `play.count` | PN-counter | сумма по всем устройствам |
| `listen.state` | LWW-register | «продолжить на другом устройстве» |
| `member.add/revoke` | add / LWW | членство и отзыв |

### 5.4 Разрешение конфликтов метаданных

Поле метаданных хранится как запись:

```rust
struct FieldVal { value: String, hlc: Hlc, dev: DeviceId,
                  source: Source /* Manual=3 > Tag=2 > Inferred=1 */ }
```

Побеждает: больший `source`, затем больший `hlc`, затем меньший `device_id`
(детерминированный тай-брейк). Ручные правки пользователя не перетираются
автоматическим перечитыванием тегов — это критично, иначе «исправил артиста»
откатится при следующем скане.

### 5.5 Удаление: три разных сценария

1. **«Освободить место»** (телефон, 3 ГБ кончились) → `blob.drop`. Трек остаётся
   в библиотеке, на других устройствах файл жив. UI: «Скачать снова».
2. **«Удалить из библиотеки»** (пользователь выбросил альбом) → `track.remove`.
   Tombstone распространяется на все устройства. Локальные файлы уходят в
   `.trash/` с TTL 30 дней (настраивается), затем GC.
3. **«Удалить физически, я сам разберусь»** → только локальная операция, без
   репликации. Нужен явный чекбокс «не синхронизировать это удаление».

Это исправление исходной идеи, где удаление на телефоне стирало файл на ПК.
Разделение `blob.drop` и `track.remove` — обязательное требование UX.

### 5.6 Модель присутствия

- `present(dev, blob)` = ∃ `blob.have(dev, blob)` и (`blob.drop` отсутствует
  или `drop.hlc < have.hlc`).
- `available(blob)` = ∃ dev: `present(dev, blob)`.
- `want(track)` = `pin` на устройстве и нет локального эквивалентного блоба.
- `want` + `available` → задача на скачивание; пир выбирается по: LAN > прямой P2P >
  релей; затем по скорости и загрузке.

## 6. Протокол синхронизации

Состояние-ориентированная репликация (state-based CRDT) с дельта-оптимизацией.

```
A → B  HELLO   {lib, dev, epoch, proto, hlc_vector}       // вектор: max HLC по каждому dev
B → A  HELLO   {..}
A → B  DIGEST  {hlc_vector, hlc_vector_summary}           // что у меня есть
B → A  OPS     [op..]                                     // <= 2000 шт / сообщение
A → B  OPS     [op..]
A → B  WANT    [blob_id..]                                // только по своим пинам
B → A  HAVE    [blob_id..]
   обмен блобами (параллельно, 2–4 потока, range/resume)
```

- Слияние: `apply(op)` проверяет подпись, epoch, идемпотентность; пишет в
  `ops` (append-only) и обновляет материализованные таблицы в одной транзакции
  SQLite.
- Компакция: каждые 10 000 операций — подписанный снапшот `snapshot(hlc, state_hash)`;
  опции `snapshot + tail`.
- Векторные часы — упрощённые: `map<dev, max_hlc>` размера = число устройств
  (обычно 2–5), это дёшево.

Для «глупой трубы» (папка/WebDAV/Nostr) операции публикуются как отдельные
объекты: `ops/<hlc_ms>-<id8>.json`. Имя детерминировано, повторная публикация
идемпотентна, конфликтов «файл vs файл» нет — слияние делает CRDT.

## 7. Транспорты (слои, включаются независимо)

| Слой | Что передаёт | Статус |
|---|---|---|
| **T0. Folder/WebDAV** | только ops (КБ) | v1, по умолчанию |
| **T1. LAN** | ops + блобы | v1 |
| **T2. Iroh P2P** | ops + блобы | v2 |
| **T3. Nostr-релей** | только ops (store-and-forward) | v2, опция |
| **T4. Пользовательский узел** | ops + блобы (кэш) | v3, опция |

### T1. LAN
mDNS (`_syncth._udp.local`) для обнаружения + QUIC с самоподписанным сертификатом,
пиннинг по отпечатку из пейринга. Скорость — скорость роутера. Никакого интернета.

### T2. Iroh
- `Endpoint` с ключом устройства; адресация по pubkey (`dial by key`, не по IP).
- `iroh-blobs`: BLAKE3 verified streaming, resumable, collections — ровно наша
  модель «контентный адрес = блоб».
- Discovery: Pkarr/DNS-пресет n0 (бесплатный) либо собственный.
- Relay: только сигналинг + фолбэк при провале hole punching (~10–20% сетей).
  **Фолбэк байтов по умолчанию выключен**; если включён — лимит (например,
  200 МБ/мес на устройство) и явная индикация в UI.

### T3. Nostr как store-and-forward
Публичные релеи бесплатны, хранят события. Публикуем зашифрованные (NIP-44)
ops в адресный «канал» библиотеки, читаем при онлайне. Даёт доставку, когда
устройства никогда не пересекаются по времени. Минусы: зависимость от чужих
релеев, метаданные утекут частично (размер/тайминг) — поэтому шифрование
обязательно и слой выключен по умолчанию.

## 8. Политики хранения (ядро продукта)

```toml
[device.phone]
budget = "40 GiB"
pin = ["liked", "recent:30d", "playlist:Running", "artist:Boards of Canada"]
stream_on_demand = true
transcode = "opus128"          # опционально, v3
network = "wifi_only"
[device.desktop]
mode = "archive"               # держим всё, что есть в библиотеке
```

- Движок политик работает как планировщик: `pin set` → `want` → очередь загрузок
  (приоритет: играющий трек > следующий в очереди > остальное).
- Эвикция: LRU по байтам среди незапиненных, но **никогда** не трогает
  `Pinned` и не удаляет единственную копию файла в библиотеке.
- Архивное устройство (ПК) — источник истины по байтам; если его нет онлайн,
  телефон стримит с любого другого пира, у которого есть блоб.

## 9. Сканирование и хеширование

1. Обход папок (ignore-правила, `.syncthignore`).
2. Быстрая проверка: `(size, mtime, inode/file_id)` против индекса → пропуск.
3. BLAKE3 потоково, многопоточно (rayon), SIMD; ~1–3 ГБ/с на ядро.
4. Chromaprint только для новых блобов (декодирование первых ~120 с).
5. Тег-парсинг (`lofty`): Vorbis/ID3/APE/MP4.
6. Всё пишется в SQLite пакетно; прогресс и ETA в UI.

Важно: BLAKE3 по всему файлу, никаких «первые 64 КБ + размер» как идентичности.
Быстрый хеш годится только как *эвристика «не изменился»* (вместе с mtime/size),
но `blob_id` должен быть полным — иначе верификация передачи и дедуп ломаются.

## 10. Плеер

- **Десктоп:** `media_kit` (libmpv) — FLAC/Opus/MP3/DSD, gapless, ReplayGain, EQ.
- **Мобильные:** `just_audio` (ExoPlayer/AVPlayer) + платформенная обвязка:
  audio focus, lockscreen/Now Playing, background service (Android
  `MediaSessionService`, iOS `MPNowPlayingInfoCenter`).
- **Стриминг по требованию:** playback через локальный HTTP-эндпоинт ядра
  (`127.0.0.1:port/blob/<id>`), который тянет range-запросы у пира и кэширует.
  Плеер ничего не знает про P2P — это важно для переиспользования либ.
- **Собственный аудиодвижок в Rust** — только если понадобится единый gapless и
  кроссфейд на всех платформах (v4, не раньше).

## 11. Стек и обоснование

### UI
| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Flutter + Rust (FFI)** | зрелые аудио-плагины, одинаковый UI, `flutter_rust_bridge` стабилен | 2 языка, размер бандла | **выбран** |
| Tauri 2 + Rust | один язык, mobile есть | mobile-аудио/фон сырые, webview-кодеки различаются | риск |
| Kotlin Multiplatform | нативный UI | нет Rust-экосистемы (BLAKE3/iroh), 3 UI-кода | нет |
| Нативно ×3 | максимум контроля | тройной объём работы, не для соло | нет |

### Сеть
`iroh` 1.0 + `iroh-blobs`. Не писать P2P самим: hole punching, QUIC, NAT-типы,
relay-фолбэк, resumable-передача — это годы работы.

### Хранилище
SQLite (WAL) + FTS5. Одна БД: `ops` (лог), `tracks`, `blobs`, `presence`,
`playlists`, `playlist_items`, `listen`, `peers`, `transfers`, `pin_rules`.
CRDT — свой минимальный слой (~400 строк) поверх SQLite, а не Automerge/Yrs:
наши структуры — множества + LWW + fractional index; generic-CRDT даст
непрозрачный блоб и потеряет возможность SQL-запросов. **ADR-кандидат.**

### Шифрование
Ed25519 (подписи), X25519 + ChaCha20-Poly1305 (конверт для «глупых труб»),
TLS 1.3/QUIC внутри Iroh. Метаданные в открытом виде не покидают устройство.

## 12. Риски и меры

| Риск | Мера |
|---|---|
| iOS убивает фон | синк только в foreground; `BGProcessingTask` на зарядке + Wi-Fi; дизайн «прерываемо и возобновляемо» |
| Android Doze | foreground service (`dataSync`), WorkManager, Wi-Fi lock на время передачи |
| Батарея | батчинг, только Wi-Fi, ограничение параллелизма, BLAKE3 вместо SHA-256 |
| NAT не пробивается (10–20%) | relay-фолбэк для ops, ожидание LAN для байтов, Tailscale как «свой» вариант |
| Никто не онлайн | store-and-forward для ops (T0/T3), байты ждут |
| Лог растёт | снапшоты + компакция, TTL для `blob.have` |
| Расхождение часов | HLC, не `SystemTime` |
| Потеря данных при удалении | корзина 30 дней, `track.remove` ≠ `blob.drop` |
| Пользователь двигает файлы | индекс по `blob_id`, путь — локальный атрибут; rescan находит переезд |
| Дубли на диске (CAS-копия) | режим «индексировать на месте» по умолчанию, hardlink/reflink где можно |
| App Store: P2P | P2P разрешён (WebRTC-подобные приложения есть), но фоновые сокеты — нет; передача только в активном приложении |
| Юридика | только личные устройства пользователя; нет публичного индекса и раздачи; AGPL |

## 13. Стоимость (честно)

| Этап | Инфраструктура | Стоимость |
|---|---|---|
| v1 (T0+T1) | нет | **0** |
| v2 (Iroh) | публичные relay/discovery n0 | **0** (ToS: dev; для продакшена — свой relay) |
| v2 прод | 1 маленький VPS под relay (сигналинг) | ~€4–6/мес на всех пользователей |
| iOS | Apple Developer Program | $99/год (неизбежно для App Store; сайдлоад — 0) |
| Windows-подпись | сертификат | ~$100/год (опционально, иначе SmartScreen) |

Итого: продукт может жить на донатах при €5–10/мес. Единственная неустранимая
статья — Apple.

## 14. Открытые вопросы

1. **Индексировать на месте или управлять файлами?** Рекомендация: на месте (v1),
   управляемый режим — позже. Риск потери данных при управлении выше.
2. **Chromaprint обязателен?** На Android/iOS нужна нативная либа (`fpcalc`).
   Фолбэк без него: `artist+title+duration` + size. Работает хуже при разных тегах.
3. **Транскодинг** — нужен ли в v3? Даёт экономию на телефоне, но +FFmpeg в бандле.
4. **iOS вообще?** Самый дорогой и ограниченный таргет. Разумно: Android+Desktop
   в v1, iOS в v4.
5. **Совместимость с Subsonic/Navidrome API** — дешёвый способ встроиться в
   существующие экосистемы; стоит ли?
