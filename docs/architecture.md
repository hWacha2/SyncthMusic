# Архитектура SynctMusic

Версия документа: 0.2 (design). Все решения ниже — рекомендации с обоснованием;
спорные места помечены **ADR-кандидатами**.

**Скоуп 0.2:** продукт — синхронизатор библиотеки, **без встроенного плеера**.
Плеер остаётся за AIMP / foobar2000 / MusicBee / Poweramp. Наша задача — чтобы у
них всегда были правильные файлы. См. §10 и ADR-001.

---

## 1. Принципы

1. **Local-first.** Каждое устройство полностью работоспособно офлайн и является
   полноправной репликой библиотеки. Сеть нужна только для обмена дельтами.
2. **Нет обязательного сервера.** Любой сетевой компонент (релей, rendezvous,
   store-and-forward) заменяем и опционален.
3. **Данные важнее файлов.** Плейлисты, лайки, история, теги — это состояние
   библиотеки, а не побочный продукт файловой системы.
4. **Никогда не терять данные пользователя.** Удаление — через tombstones + корзину;
   файлы пользователя не перезаписываются и не перемещаются без явного согласия.
5. **Файлы не покидают доверенный круг.** Передача только между устройствами с
   ключом той же библиотеки. Никакой публичной раздачи.
6. **Не подменять плеер.** Мы не воспроизводим звук. Мы управляем тем, какие файлы
   и в каком виде лежат на устройстве, и сообщаем плеерам, что появилось новое.

### ADR-001: без встроенного плеера

**Контекст.** Встроенный плеер требует аудиодвижка, фонового сервиса, MediaSession,
lockscreen-контролов, audio focus, gapless/ReplayGain и отдельной возни на iOS.
Это ~40–50% объёма работ и 100% конкуренции с AIMP и Poweramp, где у пользователя
уже есть выбор и привычки.

**Решение.** Плеера нет. Взамен: (а) файлы попадают ровно туда, где плеер их ищет;
(б) триггерим пересканирование; (в) генерируем M3U под пути этого устройства;
(г) даём контекстные действия «удалить здесь / везде».

**Последствия.**
- `core` не зависит от аудио-крейтов → меньше бинарник, проще сборка, нет
  проблем с фоновым аудио и iOS.
- Пропадает «стриминг с ПК по требованию» на Android: Poweramp не умеет HTTP.
  Компенсация: политики выборочной синхронизации + опциональный WebDAV/SMB для
  плееров, которые умеют (AIMP, foobar2000).
- Пропадает «продолжить прослушивание на другом устройстве» (это фича плеера).
- Продукт обязан быть *лучше Syncthing*, а не «удобнее Plex» — критерий качества
  смещается к политикам, дедупу и семантике удаления.

### ADR-002: библиотека = зеркало одной папки, файлы не трогаем

**Контекст.** Пользователь сам раскладывает музыку и хочет, чтобы раскладка
сохранялась на всех устройствах: выбрал папку «Музыка» на ПК и на телефоне —
и внутри неё структура одинаковая, как он её сделал. Переименование, перенос,
«причесывание» файлов недопустимы.

**Решение.** Корень библиотеки + **относительный путь входит в реплицируемое
состояние**. Модель — не «набор блобов с локальной раскладкой», а «дерево файлов,
которое обязано совпадать». Контентный адрес остаётся, но как свойство записи, а
не как замена пути.

**Последствия.**
- Отменяет более раннее «пути не реплицируются». Реплицируются, но только
  относительно корня. Абсолютный корень — локальная настройка.
- Появляются операции над записями дерева (`entry.*`) и настоящая проблема
  конфликтов «один путь — два разных файла». Решение: conflict-copy, не
  перезапись (§5.7).
- Переименование/перенос становится дешёвым: `entry.move` меняет путь, байты не
  передаются (блоб уже есть у обеих сторон).
- Выборочная синхронизация означает «на этом устройстве файла нет», но у тех
  файлов, что есть, путь совпадает. Библиотека на телефоне — подмножество дерева.
- Менеджер раскладки и «управляемый режим» из плана убираются полностью.
- Совместимость с плеерами становится тривиальной: они видят обычную папку.

## 2. Почему без сервера — и что вместо него

| Функция сервера | Замена |
|---|---|
| Хранение манифеста | CRDT-лог, полная реплика на каждом устройстве |
| Доставка дельт, когда пир офлайн | «Глупая труба»: папка/WebDAV/Nostr/git (store-and-forward) |
| Аутентификация | Подписи операций ключом устройства |
| Rendezvous (кто где) | Iroh: Pkarr/DNS-резолв по pubkey + hole punching |
| Relay для NAT | Iroh-релей для сигналинга (КБ); фолбэк байтов — выключен по умолчанию |
| Поиск/каталог | Локальный SQLite + FTS5 |

Ключевой момент: **манифест отделён от транспорта**. Лог операций — это
самодостаточный набор подписанных иммутабельных объектов. Их можно доставить
хоть по почте на флешке; результат слияния будет одинаковым.

## 3. Компоненты

```
crates/
  core/        # логика: scan, hash, db, crdt, transport, policy, integrations
  cli/         # syncth: диагностика, ручные операции
  daemon/      # syncthd: watcher, автосинк, локальный веб-UI, автозапуск
  ffi/         # flutter_rust_bridge / UniFFI glue (позже)
  shell-ext/   # Windows context menu (IExplorerCommand), опционально
app/           # UI: десктоп-трей + Android
plugins/       # AIMP / foobar2000 / проводник — отдельно от ядра
docs/
```

`core` не знает про UI и не содержит платформенного кода, кроме тонких трейтов:

```rust
trait BlobStore { fn put(&self, r: impl Read) -> Result<BlobId>; fn get(&self, id: &BlobId) -> Result<Box<dyn Read + Send>>; }
trait Platform { fn data_dir(&self) -> PathBuf; fn is_metered(&self) -> bool; fn is_charging(&self) -> bool; fn notify(&self, e: Event); }
trait Pipe     { fn push_ops(&self, ops: &[Op]) -> Result<()>; fn pull_ops(&self, since: Hlc) -> Result<Vec<Op>>; }
```

### 3.1 Демон `syncthd`

Первый слой, после которого системой можно пользоваться не из консоли:

- `notify` следит за корнем и через паузу 2 с запускает скан (файл мог
  дописываться плеером, поэтому скан «на каждый чих» вреден);
- раз в `--sync-interval` (по умолчанию 30 с) ищет пиров через UDP-discovery и
  синхронизируется; `--peer addr` и запомненные при сопряжении адреса — запасной
  путь, если broadcast не проходит;
- принимает входящие сеансы **отдельным потоком со своим SQLite-соединением**.
  Иначе два демона, одновременно инициирующие синк, зависли бы: каждый ждёт
  ответа, который может отдать только его же занятый поток;
- `tiny_http` на `127.0.0.1:47889` отдаёт встроенную страницу: состояние,
  очередь удалений, конфликты, корзина, пиры, сопряжение с QR, кнопки
  «скан / синк / пауза / GC / проверить место»;
- трей (`tray-icon`) даёт те же действия без браузера; сообщения Windows
  прокачиваются маленьким `PeekMessage`-насосом в отдельном потоке;
- `notify-rust` показывает уведомление, когда скан впервые обнаружил пропавшие
  файлы; демон при этом не удаляет ничего сам, только зовёт в UI;
- `--install-autostart` кладёт `.vbs` в Startup, который запускает демон скрыто;
- **низкий диск:** `--min-free-percent` (5%) проверяется не чаще раза в 5 с.
  При переходе через порог ставится `disk_low`, автосинк и входящие сеансы
  останавливаются, наружу отдаётся понятная ошибка, а в UI состояние
  `paused_with_warning`. Предупреждение латчится, поэтому лог не засоряется;
  после освобождения места состояние снимается автоматически.

Вся мутация реплики идёт через один рабочий поток; UI, трей и сеть шлют ему
команды. Это не микросервисная элегантность, а дешёвый способ не иметь гонок
вокруг HLC.

Страница — не «настоящий» фронтенд: цель v1 — чтобы очередь удалений и статус
были под рукой, без Flutter. Полноценный UI под Android появится отдельно.

## 4. Идентичность и пейринг

**Сейчас (Phase 0.2).** Устройство получает случайный `device_id`; библиотека
имеет общий случайный токен (32 байта hex). Строка сопряжения
`syncth://pair?v=1&dev=…&token=…&addr=IP:port` переносит токен и LAN-адрес
второму устройству; демон показывает её же QR-кодом. Сопряжённый адрес
хранится в таблице `peers`, чтобы синк работал без discovery. Отдельной
инфраструктуры, аккаунтов и обмена ключами нет.

**В планах (Phase 2+).**

- **Устройство:** Ed25519 keypair. `device_id = base32(pubkey)`. Приватный ключ —
  файл `identity.key` с правами 0600 (на Android — в Keystore, на iOS — Keychain).
- **Библиотека:** `library_id = BLAKE3(root_pubkey)`. Первое устройство генерирует
  root-ключ; остальные получают его при пейринге. Root-ключ подписывает «членство»
  (`member.add` / `member.revoke`) — это и есть access control.
- **Пейринг:** QR/строка с отпечатком TLS. Дополнительно: 6-словный код
  (BIP39-подобный) для ручного ввода. Пейринг передаёт root-ключ библиотеки —
  поэтому только по доверенному каналу (face-to-face).
- **Отзыв устройства:** `member.revoke` + ротация root-ключа (новый epoch).
  Старые операции остаются валидными; новые — только для нового epoch.

## 5. Модель данных

### 5.1 Три уровня идентичности

| Сущность | Что это | Как считается |
|---|---|---|
| `entry` | файл в дереве библиотеки | `{relpath, blob_id, size, mtime_ns, added_at}` |
| `blob_id` | содержимое файла | `BLAKE3(bytes)` |
| `track_id` | логическая запись | `BLAKE3(chromaprint \|\| duration_ms)`; фолбэк — нормализованные `artist+title+duration` |

`entry` — то, что синхронизируется как «дерево»: одинаковый `relpath` на всех
устройствах. `blob_id` — то, что передаётся и проверяется. `track_id` — то, что
позволяет понять «это тот же трек в другом файле».

Следствие: **переименование не передаёт байты** (меняется `entry.relpath`,
`blob_id` тот же), а **правка тега передаёт файл целиком** (меняется `blob_id`),
потому что байты другие. Это осознанный компромисс: просто и корректно.

Один трек → много блобов (FLAC в архиве, mp3 на телефоне). Блоб → максимум один
трек. Связь: `blob.track = track_id`.

Это решает пункт «разные теги при одном и том же аудио»: теги меняют `blob_id`, но
не `track_id`. Передача нужна только если у пира нет *эквивалентного* блоба
(проверка по `track_id` + качеству), а не по имени файла.

### 5.2 Операция (атом репликации)

```jsonc
{
  "id":     "b3:9f2c...",          // BLAKE3 канонического тела
  "lib":    "lib_7Qa...",           // library_id
  "dev":    "dev_3Kx...",           // автор (pubkey)
  "epoch":  1,                      // эпоха root-ключа
  "hlc":    [1767225600123, 4],     // [unix_ms, counter] — Hybrid Logical Clock
  "kind":   "track.upsert",
  "body":   { /* см. ниже */ },
  "sig":    "ed25519:..."
}
```

Свойства: иммутабельна, идемпотентна (по `id`), проверяема без сервера,
сериализуется в 200–800 байт.

### 5.3 Типы операций

| kind | семантика CRDT | назначение |
|---|---|---|
| `entry.put` | per-path LWW по HLC | файл появился/изменился: `{relpath, blob, size, mtime, added_at}` |
| `entry.move` | per-path LWW | перенос/переименование без передачи байтов |
| `entry.del` | per-path tombstone | файл удалён из дерева (всегда через очередь проверки, §5.5) |
| `blob.have` | grow-only set `(dev, blob)` | «у меня есть файл» |
| `blob.drop` | per-device LWW по HLC | «я удалил копию у себя» (освобождение места) |
| `blob.derived` | LWW | «этот блоб — транскод того-то» (opus для телефона) |
| `track.upsert` | field-level LWW + ранг источника | метаданные, извлечённые из тегов/фингерпринта |
| `track.pin` | OR-set по `(dev, track)` | политика хранения на устройстве |
| `playlist.set` | LWW (имя, правила) | плейлист |
| `playlist.item` | fractional index + tombstones | порядок треков |
| `member.add/revoke` | add / LWW | членство и отзыв |

Операций с воспроизведением, оценками и лайками в v1 нет: без плеера они
неоткуда взять, а оценку пользователь ставит в AIMP/Poweramp, куда мы не лезем.
`track.remove` заменён на `entry.del` + отдельное правило «убрать с других
устройств», которое пользователь подтверждает в очереди.

### 5.4 Разрешение конфликтов метаданных

Поле метаданных хранится как запись:

```rust
struct FieldVal { value: String, hlc: Hlc, dev: DeviceId,
                  source: Source /* Manual=3 > Tag=2 > Inferred=1 */ }
```

Побеждает: больший `source`, затем больший `hlc`, затем меньший `device_id`
(детерминированный тай-брейк). Ручные правки пользователя не перетираются
автоматическим перечитыванием тегов — это критично, иначе «исправил артиста»
откатится при следующем скане.

### 5.5 Удаление: три сценария + очередь проверки

1. **«Освободить место»** (телефон, место кончилось) → локальное исключение
   (`local_ignored = 1`). Трек остаётся в библиотеке, на других устройствах файл
   жив, на этом — не докачивается. UI: «Скачать снова».
2. **«Удалить из библиотеки»** → `entry_del` по блобу. Tombstone распространяется
   на все устройства. Восстановить можно, пока копия жива в локальной корзине.
3. **«Удалить физически, я сам разберусь»** → то же локальное исключение, но без
   намерения вернуть. Репликации нет.

Это исправление исходной идеи, где удаление на телефоне стирало файл на ПК.
Разделение «убрать здесь» и «удалить везде» — обязательное требование UX.

**Приоритета устройства нет.** Удаление — не автоматическая операция, а решение
человека, поэтому «главное устройство» ничего не решает и только ломает
сходимость (настройка приоритета — такое же состояние, которое нужно
реплицировать). Решение принимается по **блобу**: «удалить везде» удаляет и
перенесённые копии, «только здесь» не трогает общую библиотеку. Полная матрица
ситуаций — [sync-situations.md](sync-situations.md).

#### Удаление, сделанное чужим приложением (AIMP, Poweramp, Explorer)

Плееры удаляют файл напрямую — перехватить это нельзя (на Android — scoped
storage, на Windows — любой процесс). Поэтому удаление *по факту* детектируется,
а не перехватывается:

```
файл исчез → pending.delete{dev, blob, path, detected_at}
           → уведомление: «Удалено на ПК: 12 файлов»
              [Удалить везде] [Оставить на других] [Вернуть]
```

- `pending.delete` — **локальная** запись, не операция CRDT. Она ничего не
  реплицирует, пока пользователь не выбрал действие.
- Три исхода: `entry_del` по блобу (везде), локальное исключение (только здесь)
  или восстановление из хранилища / с другого устройства.
- Дефолт — «ничего не делать 7 дней, потом спросить ещё раз». Молчаливое
  распространение удаления на все устройства недопустимо.
- Если удаление подтверждено, но локальный файл успели изменить, он **не
  удаляется**: уходит в `*.sync-conflict-…` (см. 5.7).
- **Vault для восстановления:** перед любым удалением файла (по решению человека
  или по пришедшему `entry_del`) содержимое кладётся в `data_dir/vault/blobs/xx/…`.
  На NTFS это hardlink — 0 байт; на другом томе/ФС — обычная копия. Хранится
  30 дней (`--vault-days`), чистится `syncth vault gc`. Восстановление —
  **копия**, а не hardlink: восстановленный файл будут править тегами, и он не
  должен менять содержимое корзины. Если файла на диске уже не было к моменту
  решения (его удалили до `resolve`), корзина этого устройства пуста — но копия
  останется на другом устройстве, куда удаление пришло раньше `prune`.
  На Android hardlink через SAF недоступен, поэтому восстановление работает
  только для удалений, сделанных нашим приложением.

#### Явные действия вместо перехвата

Лучшая интеграция — не плагин, а свои точки входа:

- **Трей-меню / hotkey:** «Удалить здесь и везде».
- **Windows-проводник** (`IExplorerCommand`, `crates/shell-ext`): контекстное меню
  на папке/файле → «Synct» → «Удалить везде / только здесь».
- **AIMP:** плагин добавляет пункт меню (SDK это позволяет), но полагаться на
  pre-delete hook не стоит — если его нет, работает общий детектор.
- **Poweramp:** плагинов нет (закрытый код, есть только external API для
  управления воспроизведением), перехват невозможен. Работает только детектор +
  уведомление. Это ограничение платформы, а не недоделка.

### 5.6 Модель присутствия

- `present(dev, blob)` = ∃ `blob.have(dev, blob)` и (`blob.drop` отсутствует
  или `drop.hlc < have.hlc`).
- `available(blob)` = ∃ dev: `present(dev, blob)`.
- `want(track)` = `pin` на устройстве и нет локального эквивалентного блоба.
- `want` + `available` → задача на скачивание; пир выбирается по: LAN > прямой P2P >
  релей; затем по скорости и загрузке.

### 5.7 Конфликты в дереве

Так как путь реплицируется, возможен конфликт «один путь — два разных файла».
Правила (безопасность важнее автоматизма):

| Ситуация | Действие |
|---|---|
| Обе стороны изменили файл одновременно | оба файла сохраняются; проигравший получает имя `*.sync-conflict-YYYYMMDD-HHMMSS-<dev>.ext`; уведомление |
| Правки последовательные (сначала A, потом B) | обычное обновление, копия не создаётся (сравнение с `synced_blob` — последним согласованным блобом) |
| Первый контакт, по одному пути разные файлы | базы нет → сохраняются обе версии |
| Одна сторона удалила, другая изменила | файл остаётся, уходит в conflict-copy, удаление не теряет данные |
| Перенос + изменение на другой стороне | перенос применяется к изменённому файлу; если неоднозначно — conflict-copy |
| Один и тот же блоб по двум путям (дубль вручную) | не трогаем: это два `entry`, дедуп только помечает их в отчёте |
| Переименование `Foo.flac → foo.flac` (только регистр/NFC) | распознаётся как `entry_move`: старый путь не уходит в `pending_delete`, файл не перекачивается |
| Два реально разных файла, пути которых различаются только регистром/Unicode | не склеиваем: предупреждение в логе, ручное решение |

#### Как сканер отличает перенос от «удалил + добавил»

Сканирование двухпроходное: сначала собирается полный список файлов на диске,
затем каждый новый/изменённый файл сравнивается с живыми локальными записями.
Если блоб совпал, а старого пути на диске больше нет — это `entry_move` с
сохранённым `added_at`. Если файл ещё лежит на диске под старым путём, это
копия, а не перенос: добавляется новый `entry`, старая запись остаётся.

Сравнение путей идёт по ключу `path::key` = NFC + нижний регистр. Сам путь на
диске **не нормализуется и не переименовывается**: ключ нужен только для того,
чтобы Windows/macOS, отдающие другое написание того же пути, не превращали
переименование в удаление + добавление. Это же правило защищает `prune`:
подтверждённое удаление пропускается, если на диске есть живая запись с тем же
ключом (иначе на регистронезависимой ФС можно удалить только что
переименованный файл).

Приёмник `entry_move` не отправляет старый файл в корзину и не качает блоб
заново: он физически переставляет локальный файл (`rename`, с проверкой BLAKE3
и восстановлением `mtime`). Если локальная версия отличается — файл остаётся,
конфликт разбирает обычный `prune`/conflict-copy.

Никогда: молчаливая перезапись аудио. Потеря одного FLAC-рипа необратима, а
`*.sync-conflict` пользователь увидит и разберётся.

### 5.8 Порядок: `mtime`, `added_at` и почему «сортировка сбрасывается»

Главная жалоба при переносе музыки между устройствами — поехавший порядок.
Причины и меры:

| Что влияет | Почему ломается | Мера |
|---|---|---|
| `mtime` файла | копирование ставит «сейчас» | реплицируем `mtime_ns` и восстанавливаем после записи |
| `ctime` / creation time | нельзя задать на Android | не обещаем |
| «Date Added» в плеере | ExoPlayer/MediaStore ставит дату первого скана | не контролируется; компенсируем плейлистом |
| Порядок в альбоме | зависит от тегов `TRACKNUMBER` | читаем при индексации, экспортируем в M3U |
| Сортировка «по дате» | у всех разное определение | `added_at` (наша, реплицируемая) + M3U с явным порядком |

Вывод: **единственный надёжный способ сохранить порядок между плеерами — M3U с
нужным порядком**, сгенерированный под локальные пути (§10.2). `mtime`
восстанавливаем, чтобы «по дате изменения» тоже не ехало. Всё остальное — как
получится, и это надо честно писать в README.

## 6. Протокол синхронизации

Состояние-ориентированная репликация (state-based CRDT).

Реализовано в v1 (`crates/core/src/net.rs`): TCP, общий токен, JSON-сообщения с
длиной. Обмен **асимметричный**, чтобы две стороны не писали одновременно и не
упирались в буфер сокета на большом логе:

```
C → S  HELLO     {dev, token, proto}
S → C  HELLO_ACK {dev, proto}
C → S  OPS       [op..]              // все операции клиента
S → C  OPS       [op..]              // все операции сервера
S → C  WANT      [blob_id..]         // чего нет у сервера
C → S  BLOB_HEAD {blob, size} + байты …
C → S  DONE
C → S  WANT      [blob_id..]         // чего нет у клиента
S → C  BLOB_HEAD + байты …
S → C  DONE
```

- В конце успешного сеанса обе стороны фиксируют `synced_blob` — базу для
  определения конфликтов в следующий раз.
- Слияние: `apply(op)` проверяет `id` (BLAKE3 от тела), идемпотентность, пишет в
  `ops` (append-only) и обновляет `entries` в одной транзакции SQLite.
- Удаления применяются к диску только через `prune_deleted_files`; файл,
  не совпадающий с удаляемым блобом, спасается как conflict-copy.
- Каждый блоб проверяется по BLAKE3; `.part` удаляется при любой ошибке.
- Если серверу не хватает места, после `HELLO` он отвечает `ERROR` с понятной
  причиной, не принимая операции; клиент показывает её как ошибку сеанса.

Ещё не сделано (Phase 2+): векторные часы в HELLO, дельта вместо полного лога,
снапшоты `snapshot(hlc, state_hash)` каждые N операций, подписи Ed25519,
параллельная передача в 2–4 потока с resume.

Для «глупой трубы» (папка/WebDAV/Nostr) операции публикуются как отдельные
объекты: `ops/<blake3(op)>.op.json`. Имя детерминировано, повторная публикация
идемпотентна, конфликтов «файл vs файл» нет — слияние делает CRDT.

## 7. Транспорты (слои, включаются независимо)

| Слой | Что передаёт | Статус |
|---|---|---|
| **T0. Folder/WebDAV** | только ops (КБ) | v1, по умолчанию |
| **T1. LAN** | ops + блобы | v1 |
| **T2. Iroh P2P** | ops + блобы | v2 |
| **T3. Nostr-релей** | только ops (store-and-forward) | v2, опция |
| **T4. Пользовательский узел** | ops + блобы (кэш) | v3, опция |

### T1. LAN
mDNS (`_syncth._udp.local`) для обнаружения + QUIC с самоподписанным сертификатом,
пиннинг по отпечатку из пейринга. Скорость — скорость роутера. Никакого интернета.

### T2. Iroh
- `Endpoint` с ключом устройства; адресация по pubkey (`dial by key`, не по IP).
- `iroh-blobs`: BLAKE3 verified streaming, resumable, collections — ровно наша
  модель «контентный адрес = блоб».
- Discovery: Pkarr/DNS-пресет n0 (бесплатный) либо собственный.
- Relay: только сигналинг + фолбэк при провале hole punching (~10–20% сетей).
  **Фолбэк байтов по умолчанию выключен**; если включён — лимит (например,
  200 МБ/мес на устройство) и явная индикация в UI.

### T3. Nostr как store-and-forward
Публичные релеи бесплатны, хранят события. Публикуем зашифрованные (NIP-44)
ops в адресный «канал» библиотеки, читаем при онлайне. Даёт доставку, когда
устройства никогда не пересекаются по времени. Минусы: зависимость от чужих
релеев, метаданные утекут частично (размер/тайминг) — поэтому шифрование
обязательно и слой выключен по умолчанию.

### T4. Tailscale / WireGuard (рекомендуемый «удалённый» режим для личного использования)
Если оба устройства в одной tailnet, они видят друг друга по IP в любой сети.
Это даёт синхронизацию вне дома **без единой строки NAT-кода, релеев и DHT**.
Для личного сценария это правильный v1: T1 по LAN дома, T4 через Tailscale вне
дома, T2 (Iroh) — только если захочется «из коробки без сторонних приложений».

## 8. Что синхронизировать: подмножество дерева

Так как библиотека — зеркало папки (ADR-002), «политика» отвечает не «куда положить»,
а «какие записи дерева держать на этом устройстве». Пути при этом всегда одинаковы.

```toml
[device.phone]
root = "/storage/emulated/0/Music"
mode = "subset"
budget = "40 GiB"
include = ["Rock/**", "2024/**", "!Rock/Live/**"]
priority = ["recent:30d", "artist:Boards of Canada"]
network = "wifi_only"

[device.pc]
root = "F:\\Music"
mode = "full"          # держим всё
```

- `include`/`exclude` — glob по относительному пути. В отличие от `.stignore`, это
  **локальный** фильтр: он не влияет на другие устройства и не заставляет их
  пересылать файл снова. Исключённые записи видны в списке как «на этом
  устройстве нет» с кнопкой «скачать».
- `budget` — мягкий лимит; эвикция LRU среди не-приоритетных, но никогда не
  удаляет файл, если он единственная копия в библиотеке.
- Никакого стриминга и транскодинга: телефон играет локальные файлы.

Практическое следствие: для личного сценария («телефон — основное устройство,
ПК — бэкап») чаще всего нужен `mode = "full"` на ПК и `mode = "subset"` на
телефоне, либо `full` везде, если места хватает.

## 9. Сканирование и хеширование

1. Обход папок (ignore-правила, `.syncthignore`).
2. Быстрая проверка: `(size, mtime, inode/file_id)` против индекса → пропуск.
3. BLAKE3 потоково, многопоточно (rayon), SIMD; ~1–3 ГБ/с на ядро.
4. Chromaprint только для новых блобов (декодирование первых ~120 с).
5. Тег-парсинг (`lofty`): Vorbis/ID3/APE/MP4.
6. Всё пишется в SQLite пакетно; прогресс и ETA в UI.

Важно: BLAKE3 по всему файлу, никаких «первые 64 КБ + размер» как идентичности.
Быстрый хеш годится только как *эвристика «не изменился»* (вместе с mtime/size),
но `blob_id` должен быть полным — иначе верификация передачи и дедуп ломаются.

## 10. Интеграция с плеерами

Наш продукт не воспроизводит звук. Его KPI: **пользователь открывает свой плеер и
видит там ровно то, что ожидает, без ручных действий.**

### 10.1 Куда класть файлы

- **Куда положил пользователь — туда и кладём.** Относительный путь берётся из
  `entry.relpath` и одинаков на всех устройствах, относительно выбранного корня
  (`F:\Music` на ПК, `/storage/emulated/0/Music` на телефоне).
- Мы не переименовываем, не переносим и не «причёсываем» файлы по своей
  инициативе. Единственные исключения: conflict-copy (§5.7), `.trash` при
  удалении нашим приложением и физическое применение `entry_move` — если
  пользователь сам переименовал/перенёс файл на другом устройстве.
- Регистр и Unicode-нормализация пути сохраняются как есть; для сравнения
  используется `path::key` (NFC + нижний регистр), но диск не переписывается.
- Восстанавливаем `mtime` после записи, чтобы «сортировка по дате» не поехала.
- После записи файла: `MediaScannerConnection.scanFile` (Android) / инвалидация
  индекса (Windows, если включён), чтобы плеер увидел трек сразу, а не «после
  перезагрузки».

### 10.2 M3U под каждое устройство

Плейлисты экспортируются в `*.m3u8` с **абсолютными** путями этого устройства.
Один и тот же плейлист на ПК и телефоне выглядит по-разному — и это правильно.
Это же единственный надёжный способ зафиксировать порядок между плеерами (§5.8).
Экспорт инкрементальный: меняется один трек — переписывается один файл.

### 10.3 Стриминг «с ПК» без своего плеера

Раз встроенного плеера нет, «играть прямо с ПК» можно только средствами плеера:

- **AIMP / foobar2000** умеют открывать URL и сетевые пути → поднимаем опциональный
  read-only WebDAV-эндпоинт на архивном устройстве.
- **Poweramp** HTTP не умеет → только локальные файлы. Компенсация: политики
  выборочной синхронизации. Это осознанная потеря, см. ADR-001.

### 10.4 Обложки и sidecar-файлы

Обложка — не трек, а свойство альбома. Модель:

- `album.cover`: список блобов с рангом качества (разрешение, формат, источник).
- Канонизация: `cover.jpg` (1000 px, JPEG q85) + `folder.jpg` (для Windows-плееров)
  в папке альбома. Оригинал (3000 px, PNG) хранится как альтернатива и не
  раскладывается по умолчанию.
- Sidecar-файлы альбома (`.cue`, `.log`, `booklet.pdf`, сканы) — отдельный класс
  блобов `sidecar`, привязанный к альбому, а не к треку. Это то, что Syncthing
  раскидывает как попало и что ломает `cue`-разбивку.
- **Встраивание обложки в теги — только opt-in.** Причина в §10.5.

### 10.5 Правка тегов = новый блоб

Любая запись в файл (теги, обложка внутрь) меняет байты → меняется `blob_id` →
файл нужно заново передать на все устройства. Поэтому:

- По умолчанию файлы **не мутируются**; обложки кладутся рядом (`cover.jpg`).
- Если пользователь включил «встраивать обложки» (нужно для Poweramp, который
  читает встроенные картинки), это явная операция `blob.rewrite`, которая
  создаёт новый блоб, помечает старый как `superseded` и реплицирует замену.
- Дедуп по `track_id` (фингерпринт) гарантирует, что после перезаписи тегов
  устройства не начнут качать «новый» трек заново.

### 10.6 Чего не делаем

- Не читаем историю/оценки из баз плееров (AIMP/Poweramp) — это хрупко и
  недокументировано.
- Не управляем воспроизведением, не показываем «сейчас играет».
- Не переопределяем ассоциации файлов и не ставим себя плеером по умолчанию.

## 11. Стек и обоснование

### UI

В v1 UI — **локальная веб-страница демона** (`127.0.0.1:47889`, см. §3.1).
Этого достаточно для очереди удалений, конфликтов и статуса, и это не требует
ни Flutter, ни установки трея. Ниже — соображения на будущее, когда появится
Android и полноценный десктоп-клиент.

Без плеера главный аргумент за Flutter (зрелое аудио) исчез. Осталась задача
«список библиотеки + политики + статус синхронизации + диалоги», и здесь Tauri 2
становится реальным конкурентом: один язык (Rust + web), меньше бинарник, живой
десктоп-трей и системные интеграции.

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Flutter + Rust (FFI)** | один UI на Win/Android; зрелые плагины SAF, foreground service, notifications; `flutter_rust_bridge` | 2 языка, 50 МБ бандл, десктоп «не нативный» | **выбран для v1** |
| Tauri 2 + Rust | один язык, 10 МБ, быстрый старт, удобные tray/window/shell | Android: SAF + foreground service + уведомления делать самому; mobile-часть сырая | лучший вариант, если Android отложить |
| Slint (Rust) | чистый Rust, нативно | экосистема для списков/шрифтов/форм слабая, Android-интеграция через Kotlin | нет |
| Kotlin MP + Compose | нативный Android | второй биндинг-слой (UniFFI), десктоп-часть слабее | нет |

Решение остаётся за Flutter **из-за Android**: именно там боль (SAF, фон, media
scan, разрешения), и там у Flutter больше готовых кирпичей. Если выяснится, что
Android можно отложить на полгода — переход на Tauri будет дешевле, чем кажется:
интерфейс тонкий, вся логика всё равно в Rust.

### Сеть
`iroh` 1.0 + `iroh-blobs`. Не писать P2P самим: hole punching, QUIC, NAT-типы,
relay-фолбэк, resumable-передача — это годы работы.

### Хранилище
SQLite (WAL) + FTS5. Одна БД: `ops` (лог), `tracks`, `blobs`, `presence`,
`albums`, `covers`, `sidecars`, `playlists`, `playlist_items`, `pending_deletes`,
`vault`, `peers`, `transfers`, `pin_rules`, `m3u_export`.
CRDT — свой минимальный слой (~400 строк) поверх SQLite, а не Automerge/Yrs:
наши структуры — множества + LWW + fractional index; generic-CRDT даст
непрозрачный блоб и потеряет возможность SQL-запросов. **ADR-кандидат.**

### Шифрование
Ed25519 (подписи), X25519 + ChaCha20-Poly1305 (конверт для «глупых труб»),
TLS 1.3/QUIC внутри Iroh. Метаданные в открытом виде не покидают устройство.

| Риск | Мера |
|---|---|
| iOS убивает фон | синк только в foreground; `BGProcessingTask` на зарядке + Wi-Fi; дизайн «прерываемо и возобновляемо» |
| Android Doze | foreground service (`dataSync`), WorkManager, Wi-Fi lock на время передачи |
| Батарея | батчинг, только Wi-Fi, ограничение параллелизма, BLAKE3 вместо SHA-256 |
| NAT не пробивается (10–20%) | relay-фолбэк для ops, ожидание LAN для байтов, Tailscale как «свой» вариант |
| Никто не онлайн | store-and-forward для ops (T0/T3), байты ждут |
| Лог растёт | снапшоты + компакция, TTL для `blob.have` |
| Расхождение часов | HLC, не `SystemTime` |
| Потеря данных при удалении | корзина 30 дней + очередь `pending.delete`; удаление не реплицируется без подтверждения |
| Пользователь двигает/переименовывает файлы | `entry.move`, байты не передаются; ключ пути NFC+регистр; при неоднозначности — conflict-copy |
| Дубли на диске | копий не делаем: библиотека — это та же папка; Vault на Windows через hardlink (0 байт) |
| App Store: P2P | P2P разрешён (WebRTC-подобные приложения есть), но фоновые сокеты — нет; передача только в активном приложении |
| Юридика | только личные устройства пользователя; нет публичного индекса и раздачи; AGPL |
| Нет стриминга на Android (ADR-001) | честно писать «выборочная синхронизация», а не «стриминг»; WebDAV для AIMP/foobar |
| Плеер удалил файл, мы не знаем зачем | очередь `pending.delete` + уведомление; никогда не реплицировать удаление молча |
| Poweramp не поддерживает плагины | не обещать; работать через детектор файлов и наш UI |
| Правка тегов ломает `blob_id` | по умолчанию не мутировать; `blob.rewrite` как явная операция |
| Плеер правит теги прямо во время синка | хешируем после стабилизации mtime (debounce 2 с), передаём только закрытые файлы; `EBUSY`/`LOCK` — повтор |
| Android: нет inotify для SAF | для личного использования — All Files Access + `FileObserver`; иначе периодический рескан (при открытии, WorkManager) |
| Конфликт «изменили оба» | conflict-copy, никогда не перезапись (§5.7) |
| «Порядок поехал» | `mtime` восстанавливаем, порядок фиксируем M3U; «Date Added» плеера не контролируем |

## 14. Открытые вопросы

1. ~~Индексировать на месте или управлять файлами?~~ → **решено: на месте** (ADR-002).
2. **Chromaprint обязателен?** На Android/iOS нужна нативная либа (`fpcalc`).
   Фолбэк без него: `artist+title+duration` + size. Работает хуже при разных тегах.
3. ~~Транскодинг~~ → **не нужен** в модели «зеркало папки»: файл либо есть, либо нет.
4. **iOS вообще?** Без плеера и без общего UI смысл близок к нулю. Отложено
   бессрочно.
5. **Совместимость с Subsonic/Navidrome API** — дешёвый способ встроиться в
   существующие экосистемы; стоит ли?
6. **Обложки: `cover.jpg` или встраивание?** Для Poweramp нужно встраивание (он
   читает теги), для AIMP достаточно `folder.jpg`. Рекомендация: `cover.jpg` по
   умолчанию, встраивание — opt-in на конкретном устройстве.
7. **Кто чинит теги?** Пользователь правит их в AIMP/Poweramp, мы синхронизируем
   изменённый файл. Свой редактор тегов в v1 не делаем; позже — пакетные операции
   («дата из имени папки», «номер трека из имени файла»).
