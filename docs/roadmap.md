# План работ

Формат: фазы сдаются независимо, каждая заканчивается работающим артефактом.
Оценки — для одного разработчика, без учёта «полировки до продакшена».

Цель: как можно раньше дойти до **двух устройств с одной библиотекой** на
минимальной инфраструктуре (0 серверов), и только потом наращивать.

---

## Phase 0 — Ядро (2–3 недели)

Никакого UI. Только `crates/core` + `crates/cli`.

- [ ] Cargo workspace, CI (fmt, clippy, test), лицензия AGPL-3.0
- [ ] Схема SQLite + миграции (`rusqlite`/`sqlx`, WAL, FTS5)
- [ ] Сканер: обход, `size+mtime+file_id` эвристика, BLAKE3 (rayon), `lofty`-теги
- [ ] Chromaprint (`fpcalc`-биндинг или `rusty-chromaprint`), фолбэк без него
- [ ] HLC, каноническая сериализация (CBOR), подписи Ed25519
- [ ] `Op`-типы из §5.3 + `apply()` + материализация в SQL
- [ ] Снапшоты и компакция лога
- [ ] LAN-транспорт: mDNS + QUIC (self-signed, pinning) + `blob get` с диапазонами
- [ ] `Pipe::Folder` — экспорт/импорт ops в директорию
- [ ] CLI: `scan`, `status`, `pair`, `sync`, `serve`, `verify`

**Готово, когда:** две машины, общая папка для ops, `syncth sync` на обеих →
одинаковый `state_hash`; файл переезжает по LAN; `syncth verify` подтверждает
все блобы.

**Бенчмарк, который надо снять сразу:** скорость сканирования 100 ГБ FLAC на
целевом железе (нужно ≥ 300 МБ/с на HDD, ≥ 1 ГБ/с на SSD, иначе UX плохой).

## Phase 1 — Десктоп-приложение (4–6 недель)

- [ ] Flutter + `flutter_rust_bridge`, `core` как единый источник состояния
- [ ] Библиотека: список, поиск (FTS), фильтры, обложки (из тегов/папок)
- [ ] Плеер: `media_kit`, очередь, gapless, ReplayGain, hotkeys, MPRIS/SMTC
- [ ] Пейринг по QR (генерация/скан) + ручной код
- [ ] Экран синхронизации: пиры, статус, очередь, скорость, конфликты
- [ ] Плейлисты (fractional index), лайки, оценки — всё через CRDT
- [ ] «Освободить место» vs «Удалить из библиотеки» — разные действия в UI
- [ ] Онбординг: выбрать папку → скан → прогресс → пейринг

**Готово, когда:** два ПК (Windows/Linux) держат одну библиотеку; плейлист,
созданный на одном, появляется на другом; удаление ведёт себя по §5.5.

## Phase 2 — Android (4–8 недель)

Самый рискованный этап: фон, батарея, storage permissions.

- [ ] Storage Access Framework, persistable URI permissions
- [ ] Foreground service + WorkManager, политика «только Wi-Fi / только на зарядке»
- [ ] Плеер: `just_audio`, MediaSession, lockscreen, audio focus, bluetooth
- [ ] Модель пинов: бюджет места, правила, эвикция LRU
- [ ] Стриминг по требованию с ПК: локальный HTTP-эндпоинт + кэш
- [ ] Возобновление прерванных передач (сеть ушла — очередь ждёт)
- [ ] Экран «Скачать на устройство» / «Держать офлайн»

**Готово, когда:** телефон 128 ГБ держит 30 ГБ закреплённого, остальное играет
с ПК по Wi-Fi без задержек; после перезагрузки очередь продолжается.

## Phase 3 — Интернет-P2P (3–4 недели)

- [ ] `iroh` endpoint, ключ устройства, `iroh-blobs` как хранилище/транспорт
- [ ] Discovery (Pkarr/DNS), relay-конфиг с переопределением (свой/пустой)
- [ ] Матрица соединений: LAN > direct > relay, с телеметрией успеха
- [ ] Опциональный Nostr-канал для ops (шифрование NIP-44, выключен по умолчанию)
- [ ] Лимиты фолбэк-трафика, индикация в UI, «не использовать релей»
- [ ] Тесты в «плохих» сетях: CGNAT, симметричный NAT, мобильный оператор

**Готово, когда:** телефон в LTE, ПК за домашним NAT → трек доезжает напрямую
в большинстве сетей, а без прямого соединения — ждёт LAN, не жжёт трафик.

## Phase 4 — «Продукт, а не прототип» (ongoing)

- [ ] Синхронизация позиции прослушивания («продолжить на телефоне»)
- [ ] Импорт/экспорт: M3U, iTunes XML, Subsonic-совместимый API (ADR)
- [ ] Умные плейлисты и правила пинов (жанр/год/BPM/дата добавления)
- [ ] Дедупликация и «апгрейд качества» (mp3 → FLAC автоматом)
- [ ] Транскодинг в opus для телефона (кэш производных блобов)
- [ ] Диагностика: `syncth doctor`, экспорт логов, понятные ошибки
- [ ] Доставка: GitHub Releases, F-Droid, winget/brew, автообновление
- [ ] Документация для пользователя: «5 минут до первой синхронизации»

## Phase 5 — iOS и расширения

- [ ] iOS: BGTaskScheduler, Keychain, MPNowPlayingInfoCenter (только при
      наличии $99/год — единственная неизбежная статья расходов)
- [ ] Плагины/скрипты, headless-демон для NAS
- [ ] Опциональный «свой узел» (Raspberry Pi / старый телефон) как всегда-онлайн кэш
- [ ] Шаринг плейлистов между людьми (только метаданные, без файлов)

## Порядок, который я бы не менял

1. **Сначала CLI и e2e-тест на двух машинах.** UI на нестабильном ядре съест
   втрое больше времени.
2. **Сначала «папка для ops», потом Iroh.** Folder-транспорт — 100 строк, и он
   сразу доказывает корректность CRDT без сетевой отладки.
3. **Сначала Android, потом iOS.** iOS-ограничения могут заставить переделать
   фоновую модель; лучше узнать это после того, как модель устоялась на Android.
4. **Не писать аудиодвижок.** `media_kit`/`just_audio` закрывают 95% задач.

## Критерии «не провалили проект»

- Синхронизация 10 000 треков / 1 ТБ: инкрементальный скан < 2 с, дельта ops < 100 КБ.
- Новое устройство подключается к полной библиотеке и получает метаданные < 60 с.
- Ни одна операция не требует сервера.
- Пользователь ни разу не видит слово «хеш», «blob» или «CRDT».
