# Живая сессия решений

Статус: спецификация принята; этапы 1–4 сделаны, дальше Android-сервер.

Документ описывает модель ручной синхронизации: подключение, общий план
изменений, решения по каждому пути и отдельную фазу передачи. Он дополняет
[architecture.md](architecture.md) §6 и заменяет прежнюю модель «нажал
синхронизировать — всё применилось сразу».

## 1. Принципы

1. **Только по кнопке.** Автосинк и фоновый watcher по умолчанию выключены.
   Скан, подключение и передача запускаются человеком.
2. **Сначала показать, потом делать.** Манифест и решения не меняют ни журнал,
   ни диск. Файлы передаются и удаляются только после подтверждения.
3. **Решение принимает человек, а не устройство.** Главного устройства нет;
   решения живут отдельно от журнала операций и привязаны к паре устройств.
4. **Ничего не удаляется молча.** Удаления выключены по умолчанию и требуют
   явной галочки. Отклонённое удаление имеет два разных исхода.
5. **Одно соединение — одна сессия.** Оба устройства видят один и тот же список
   и могут менять решения, пока не начата передача.

## 2. Состояния соединения

```
нет соединения ──«Подключиться»──► подключение ──успех──► сессия (план)
       ▲                              │                      │
       └──────── «Отключиться» ◄──────┴──────────────────────┘
```

- **Нет соединения.** Локальные изменения видны на экране плана, кнопка
  «Синхронизировать» заблокирована. Данные не передаются.
- **Подключение.** TCP-сеанс, `Hello`/`HelloAck`, обмен манифестами и
  построение плана. Сокет остаётся открытым на всё время сессии.
- **Сессия.** Обе стороны видят общий план. Изменения решений рассылаются
  push-сообщениями. Commit разрешён с любого устройства.
- **Передача.** Решения заблокированы, идут блобы и удаления.
- **Отключиться.** Закрывает сокет, скрывает commit, показывает «Нет
  соединения». Пир и токен библиотеки сохраняются.
- **Забыть устройство.** Отдельное действие: удаляет запись из `peers`.

Пассивный UDP-discovery работает и без сессии: он только обновляет адреса
сохранённых пиров. Данные по нему не идут.

## 3. План

План строится один раз при подключении и замораживается.

```rust
struct Plan {
    peer_dev: String,
    peer_name: String,
    created_at: u64,
    expires_at: u64,          // 15 минут
    local: Vec<Change>,       // что изменилось на этом устройстве
    remote: Vec<Change>,      // что изменилось у пира
    conflicts: Vec<Conflict>,
    decisions: DecisionSet,
    version: Hlc,             // версия набора решений
}
```

Строка изменения:

```rust
struct Change {
    path: String,
    from: Option<String>,     // для moved — старый путь
    kind: ChangeKind,         // added | updated | moved | deleted
    side: Side,               // local | remote (источник события)
    blob: String,
    base_blob: String,        // последний согласованный блоб (synced_blob)
    size: u64,
    mtime_ns: i64,
    present: bool,            // файл реально есть на этом устройстве
    ignored: bool,
}
```

Правила построения:

- локальная правка: `entries.blob != synced_blob` или путь есть в
  `pending_deletes`;
- удалённая правка: операция пира с блобом, отличным от `synced_blob`, или
  `entry_del`;
- обе стороны изменили один путь разными блобами — конфликт;
- пустой `synced_blob` и разные блобы с двух сторон — тоже конфликт;
- `entry_move` показывается как «перенесён», но применяется парой
  «добавить новый путь / убрать старый»;
- построение плана ничего не пишет в БД и на диск.

План хранится в БД (`sync_plans`) с TTL 15 минут. Новый скан, смена блоба или
commit инвалидируют его. Просроченный план не применяется.

## 4. Решения

Карточка описывает событие и его **источник**: «На этом ПК», «На телефоне».
Текст всегда строится от источника; на другом устройстве меняются только
имена. Кнопок внутри карточек нет: человек отмечает чекбоксами одинаковые
события (один источник + один тип) и нажимает действие в плашке снизу.
Смешивать типы и стороны в одном выделении нельзя.

| Событие у источника | `Accept` — применить на втором устройстве | `Revert` — отменить у источника | `OnlyHere` — оставить только там, где файл есть сейчас |
|---|---|---|---|
| Добавлен файл | «Добавить на второе устройство» | «Убрать у источника» | «Оставить только у источника» |
| Изменён файл | «Применить на второе устройство» | «Вернуть версию со второго устройства» | — |
| Перенесён файл | «Перенести на второе устройство» | «Вернуть старый путь у источника» | — |
| Удалён файл | «Удалить и на втором устройстве» (`DeleteEverywhere`) | «Вернуть файл у источника» (`KeepInLibrary`) | «Оставить только на втором устройстве» |

Смысл действий:

- `Accept` — событие применяется на втором устройстве.
- `Revert` — событие отменяется там, где произошло: добавление убирается,
  правка или перенос возвращает прежнюю версию, удаление возвращает файл.
- `OnlyHere` — путь помечается `local_ignored` на стороне, где файла нет;
  файл остаётся только там, где он есть сейчас. Для добавления это источник,
  для удаления — второе устройство.
- Для правки и переноса третьего действия нет: «ничего не делать» оставило бы
  на двух устройствах разные блобы одного пути. Для добавления и удаления
  `OnlyHere` — осознанное постоянное расхождение, а не «отложить».
- Конфликты решаются отдельно: «Взять версию этого устройства» (`Keep`),
  «Взять версию второго» (`Accept`), «Оставить обе» (`KeepBoth`).
- Пока решение не выбрано, действуют умолчания: добавления, правки и переносы
  приняты (`Accept`), удаления не применяются (`Keep` — «Остаётся», без
  пометки `OnlyHere`). Конфликт без решения — «Требует решения».
- Групповое действие создаёт отдельное решение для каждого выбранного пути;
  каждое получает HLC и сохраняется в БД.
- При подключении стороны обмениваются решениями и сливают их по HLC
  (last-write-wins по пути).
- Офлайн-решения не истекают по времени: они сбрасываются, если у пути
  изменился блоб или путь исчез из журнала.

## 5. Протокол

`PROTO = 3`. Один TCP-сеанс, push-сообщения в обе стороны.

```
C → S  HELLO        {dev, name, token, proto, have}
S → C  HELLO_ACK    {dev, name, proto, have}
C → S  PREVIEW      {ops, decisions}      // манифест и сохранённые решения
S → C  PREVIEW_ACK  {ops, decisions, version}
...                                         // сессия открыта
C ↔ S  DECISION     {path, action, blob, hlc, dev}  // push при изменении
C ↔ S  DECISION_STATE {hash, version}       // сводка набора решений
C ↔ S  HEARTBEAT                             // раз в 10 с
C → S  COMMIT        {decisions_hash}
S → C  COMMIT_GO                            // хэш и план проверены
C → S  COMMIT_PLAN   {ops, needs}           // свои операции и чего не хватает
S → C  COMMIT_PLAN   {ops, needs}
C → S  WANT          {blobs, offsets}       // offsets — докачка с длины .part
S → C  BLOB_HEAD / байты / DONE
S → C  WANT          {blobs, offsets}
C → S  BLOB_HEAD / байты / DONE
C ↔ S  COMMIT_READY                          // все блобы скачаны и проверены
C ↔ S  COMMIT_DONE    {accepted, rejected}   // применено на каждой стороне
```

`PREVIEW` передаёт не только решения, но и операции: обе стороны строят план
из чужого манифеста, ничего не применяя. `PREVIEW_ACK` возвращает свой
манифест, объединённый набор решений и версию плана. Полный обмен
`OPS/WANT/BLOB` остаётся только как временный путь кнопки
«Синхронизировать»; commit его не использует.

- Commit может начать любая из сторон: сообщение `COMMIT` идёт по тому же
  сокету, вторая сторона отвечает `COMMIT_GO` и проходит зеркальный обмен.
  Применяется только при совпадении `decisions_hash`; иначе ответ «план
  разошёлся» и перестроение.
- После старта передачи решения read-only.
- Сначала скачиваются и проверяются **все** блобы, потом применяется план.
  Обрыв не меняет ни диск, ни журнал: решения сохранены, commit повторяется.
- Докачка: недокачанный блоб лежит в `<data_dir>/incoming/<blob>.part`.
  Повторный commit сообщает пиру `offset` (длину `.part`) и продолжает с того
  же байта. Файл становится валидным только после полной загрузки и проверки
  BLAKE3: тогда он переименовывается в `.blob`, применяется и удаляется.
- Передача блобов двунаправленная: исполнитель может и отдавать файл
  (восстановление из корзины), а не только скачивать.
- `BLOB_NEED` обслуживается только сопряжёнными пирами, в том числе из
  корзины пира. Если блоб уже вычищен GC (TTL корзины 30 дней), кнопка
  «Вернуть файл у источника» недоступна.

## 6. Семантика удалений

Удаление, пришедшее с пира, никогда не применяется автоматически.

| Действие пользователя | Результат |
|---|---|
| `Accept` / «Удалить и на втором» | `EntryDel` применяется, файл уходит в корзину на обеих сторонах |
| `Revert` / «Вернуть файл у источника» | новый `EntryPut`; файл скачивается из живого файла или корзины второго устройства |
| `OnlyHere` / «Оставить только на втором» | `local_ignored = 1` на стороне без файла; путь больше не возвращается туда |
| `Keep` (по умолчанию) | удаление не применяется и не фиксируется навсегда; путь останется в следующем плане |

Если файла нет ни на втором устройстве, ни в его корзине, `Revert` недоступен;
в UI показывается причина.

## 7. Скан и папка

- Первый запуск: системный диалог выбора папки **и** ручной ввод пути.
  На ПК — `rfd::FileDialog` + текстовое поле, на Android — список каталогов +
  текстовое поле (SAF отложен).
- Повторный запуск папку не спрашивает: корень хранится в конфиге ПК и в
  `meta` БД на Android.
- «Пересканировать» только обновляет локальный журнал. Сеть не участвует.
- Смена корня не должна превращать старые пути в массовые удаления: требуется
  явная переиндексация корня (сброс локального присутствия, не журнала).

## 8. UI

- Единый экран **«План синхронизации»**; отдельной вкладки «Удаления» нет:
  `pending_deletes` показываются в общем плане.
- Экран доступен всегда: без пира видны локальные изменения, commit
  заблокирован, рядом «Нет соединения».
- Фильтры: «Все», «Добавленные», «Изменённые», «Перенесённые», «Удалённые»,
  «Конфликты».
- Карточки сгруппированы по источнику и типу события. В карточке только путь,
  размер, время и метка устройства; кнопок действий внутри нет.
- Чекбокс на карточке; выделять можно только события одной группы
  «источник + тип». При выделении снизу появляется плашка: «Выбрано: N»,
  действия этой группы, «Выбрать все» и «Снять».
- Групповое действие применяется ко всем выбранным путям сразу.
- В устройствах у сохранённого пира есть «Подключиться» и «Забыть».
- Пока сессия открыта — статус связи, имя пира, кнопка «Отключиться».
- Во время передачи — полоса прогресса по файлам и байтам; решения read-only.

## 9. Этапы работ

1. ✅ **Ручной режим.** Автосинк и watcher выключены по умолчанию; ручной ввод
   пути на ПК; управление пирами (`connect`/`disconnect`/`forget`); расширенный
   статус (`connection`, `peers`, `last_sync`).
2. ✅ **Модель плана.** `plan.rs`, таблица решений, HLC-LWW, инвалидация,
   тесты на все виды изменений.
3. ✅ **Preview-сессия.** `PROTO = 3`, `PREVIEW`/`PREVIEW_ACK`, живой канал
   решений (`DECISION`, `DECISION_STATE`, `HEARTBEAT`), план с TTL 15 минут,
   `/api/plan` и `/api/decision`. Старый `PROTO = 2` получает понятный отказ.
4. ✅ **Commit.** `COMMIT`/`COMMIT_GO`/`COMMIT_PLAN`/`COMMIT_READY`/
   `COMMIT_DONE`, хэш набора решений, применение выбранного, двунаправленные
   блобы с докачкой `.part`, `BLOB_NEED` из корзины, `/api/commit`.
5. **Android-сервер.** Приём входящих при открытом приложении, foreground
   service позже, MediaScanner.
6. **UX.** Единый экран «План синхронизации» вместо вкладки «Удаления»:
   карточки с чекбоксами, плашка группового решения, фильтры, прогресс,
   подключение/отключение.
7. **Документация.** README, roadmap, sync-situations.

## 10. Тесты

- построение плана не меняет ни БД, ни диск;
- конфликт определяется до применения;
- commit применяет только выбранное;
- `Accept` применяет событие на втором устройстве;
- `Revert` отменяет добавление/правку/перенос у источника;
- `OnlyHere` для добавления и удаления оставляет файл только на одной стороне;
- у правки и переноса нет третьего действия;
- групповое решение применяется ко всем выбранным путям одной группы;
- отклонённое удаление не удаляет файл и сходится при следующем сеансе;
- «вернуть файл у источника» работает из корзины пира;
- просроченный или разошедшийся план не применяется;
- обрыв сессии сохраняет решения;
- докачка продолжает `.part` с того же байта, `.part` исчезает только после
  проверки BLAKE3;
- `KeepBoth` оставляет обе версии на обоих устройствах;
- preview не применяет операции и не трогает файлы;
- решение, записанное в БД сервера, доезжает по живому каналу;
- входящий сеанс на Android-подобной среде;
- старый клиент `PROTO = 2` получает понятный отказ.
